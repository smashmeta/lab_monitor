Four libraries, two applications

lab_monitor Architecture

A central server discovers client machines over DDS, reconciles them against an expected-host list, and distributes a template of compliance rules. Clients report resource usage and rule compliance back. Here is how the pieces are separated, and what actually crosses between them.

The modules

Everything is layered so that lm_core sits at the bottom knowing nothing about Qt, DDS or the operating system, and the two applications sit at the top composing the rest. Each library owns one kind of knowledge.

Build targets, their dependencies, and their unit tests
Target What it knows Depends on Tests

lab_monitor_client Hidden tray agent; a worker thread samples, evaluates and publishes all four 17
lab_monitor_server Fleet console: discovery, reconciliation, template authoring and publishing all four 34

345 unit tests in total, plus four Fast DDS loopback integration tests gated behind LM_BUILD_INTEGRATION_TESTS because they need loopback multicast.

All four libraries are shared, and that is what those test counts are worth. A test binary and an application load the same lm_core.dll — not a second static copy of the same code, with a second copy of every global inside it. Every executable and every DLL builds into one directory, build/<preset>/bin/<config>, because Windows resolves a DLL from the loading executable's own folder: without that, each test binary would need its own copy and "the same binary" would be a claim about copies rather than a fact. There is exactly one lm_core.dll in the build tree.

The load-bearing constraint: lm_core depends on nlohmann-json and nothing else. No Qt, no DDS, no syscalls, no Boost. That is what makes evaluate() and reconcile() testable without a single mock — the 135 core tests call plain functions with plain structs. Adding another dependency to libs/core is a design violation, not a convenience.

Who owns what

A dependency arrow says one library may name another's types. It does not say who holds an instance, or who is allowed to reach for one. Those two questions are where the real coupling lives, so here is every principal type with its owner and its users — inside its own component and outside it.

Four kinds of holding appear, and the label under each owner says which: by value a direct member, destroyed with its owner; unique_ptr exclusive and injected through a constructor; qt parent a child widget or object, deleted by its parent; borrowed a raw pointer that owns nothing and must outlive nothing.

lab_monitor_server

TypeOwned byUsed by
ServerController main(), deleted after the window and only once stop() has torn the transport down. borrowed Owns the transport, the registry, the fleet model, the coalescer, the expected-host list and both bundles. Everything the window knows it learns from here, by signal or by accessor.

Two patterns run through all of it. Every cross-component dependency is injected, never reached for — probes and transports arrive through a constructor, chosen once in main(), which is what lets a test swap in a fake or an in-memory bus without either application knowing. And every borrowed pointer points from the shorter-lived object to the longer-lived one: the tray borrows the window and dies first, the window borrows the controller and dies first. Where that ordering is load-bearing, it is written down at the delete site rather than left to be rediscovered.

One honest wrinkle. The server links lm_platform but does not use a single symbol from it — no header from it is included anywhere in apps/server. It is a dependency the module table above lists because the build file does, not because the code needs it. Dropping it would cost the server nothing.

What crosses the wire

Four topics, and only four. Three flow client → server; one flows back. Their quality-of-service settings differ because what they carry differs: a resource sample is worthless a second later, while an announce is the only carrier of a client's capabilities.

ClientAnnounce
reliable · transient local
Host id and capabilities, every 10 s. It repeats on a timer rather than announcing once, because the server can forget: a liveliness drop erases the registry entry outright, and the samples that keep arriving recreate it knowing nothing about capabilities.
ResourceSample
best effort · volatile
CPU, memory, per-mount disk and the full network adapter list, every 2 s. Deliberately lossy: a dropped sample is replaced two seconds later, and reliability would only build a queue of stale readings.
ComplianceReport
reliable · transient local
One CheckResult per rule — id, status, what was observed, what was expected — every 30 s. It carries no rule descriptions; both ends recover those from the bundle they already hold.
TemplateBundle
reliable · transient local
Server → client, on publish. The one topic travelling downward: the baseline, every template, and the per-host assignments.

The fields on the wire

The four payloads are small and flat, which is why libs/transport/src/codec.cpp encodes them by hand rather than through fastddsgen — that is a Java tool, is not a vcpkg port, and there is no JDK here. Fields are written in declaration order, and decode() is hardened against hostile input: element counts read off the wire drive a capped reserve rather than a resize, and both fastcdr::exception::Exception (which does not derive from std::exception) and std::exception are caught.

ClientAnnounce

client → server · every 10 s reliable · transient local · keyed by host_id
host_id string The machine's hostname, from local_host_name(). The key on every other topic, and the join between a fleet row, a sample and a report.
agent_version string Which build of the client is running. Informational — nothing branches on it yet.
capabilities uint32 Capabilities::raw(), a bitmask: Resources 1, Processes 2, Services 4, Registry 8, Network 16. A rule whose capability is missing evaluates to NotApplicable rather than Fail, and the server shows – instead of a count. This single field is why the announce repeats on a timer: it is the only carrier of it.

ResourceSampleMessage

client → server · every 2 s best effort · volatile · keep last 1
host_id string Which machine this reading came from.
cpu_percent double 0–100. Computed as a delta against the previous probe, so the first sample after a client starts reads 0.

mem_used_bytes uint64 In use. The percentage is derived at the display, not sent.

DiskUsage — one per mount

NetworkAdapter — one per interface

name string What the machine's own UI calls it — "smash-wifi", the renameable name in Windows' Network Connections. Not unique in principle, which is what id is for. Rules match on this, case-insensitively, because rules are typed by people.
description string The hardware behind it: "Intel(R) Centrino(R) Advanced-N 6205".
id string The system's stable identifier — a GUID on Windows, eth0 on Linux. Unique and unchanging where the name is neither, so any future matching keys on it. Shown only on hover.
type enum Unknown, Ethernet, WiFi, Loopback, Ppp, Tunnel, Modem, Other. Other means a type was reported that we do not name; Unknown means the platform did not say.
link enum Unknown, Connected, NoMedia, Disconnected, Connecting, Disabled, Faulted. Deliberately not a boolean: a port with nothing plugged in, a card switched off, and an idle dial-up entry are three different problems that "not connected" would flatten into one. Only Connected counts as up.

Deliberately absent

IP addresses — This message answers "what is this machine plugged into, and is it up", not "how is it routed". Addresses would also churn the sample under DHCP, defeating the equality check that suppresses no-op updates.

TemplateBundleMessage

server → client · on publish reliable · transient local · keep last 1
revision uint64 Bumped on every publish. A client that has already applied this revision short-circuits, which is what makes a server restart's re-announce free.
hash string Content hash of the bundle.

ComplianceReportMessage

client → server · every 30 s reliable · transient local · keyed by host_id

applied_revision uint64 Which bundle the results were produced against. This is how the server tells a client that is still running old rules — the fleet table's Stale column.

CheckResult — one per rule

rule_id string The only join back to the rule. No description travels, so each end recovers the display text from the bundle it already holds. Ids are generated from the rule's kind and target rather than typed, because a reused id silently dropped a rule from evaluation.
status enum Pass, Fail, NotApplicable, Error. Only Fail counts against compliance; NotApplicable is left out of the denominator entirely, while Error stays in it — "could not check it" is not "passed".
observed string What was actually seen, in the reader's terms: "2 of 4 connected", "running, version 1.4".
message string For an Error, the cause. For a Fail, what was expected instead — "expected at least 1 connected". Without it a failure states only the observation, leaving the reader to work out which rule that violates. Empty for Pass, whose observed already says everything.

Inside the client

The client starts hidden — there is only a tray icon until someone opens the detail window. All probing and messaging happens on a worker thread, which talks to the GUI exclusively through queued signals, so nothing on the GUI thread ever blocks on a probe.

Inside the server

ServerController owns the transport, the registry, the expected-host list and both bundles — the one that has been published and the draft being edited. It lives entirely on the GUI thread. Fast DDS invokes its callbacks on its own internal threads, and every one of them is marshalled across before it touches the registry, because ClientRegistry is deliberately not thread-safe.

The two functions everything else serves

Strip away the threads, the widgets and the wire and the system reduces to two pure functions in lm_core. Both take every input as an argument — including the clock — and return a value. Neither reads a file, opens a socket, or touches global state, which is why they carry the bulk of the test suite.

evaluate() — what this machine is, against what it should be

ComplianceReport evaluate(const TemplateBundle& bundle,
                          const HostFacts& facts,
                          Capabilities caps);

It runs on the client, on the worker thread, every 30 seconds. Three arguments, and each comes from a different place with a different lifetime.

bundle — const TemplateBundle&

Origin
The server. An operator edits the draft and presses Publish; the bundle travels as JSON on the TemplateBundle topic; MonitorWorker::on_bundle() parses it and stores it in its bundle_ member.
Lifetime
Owned by the worker, and it outlives any single evaluation — it is replaced wholesale when a new revision arrives, never mutated in place. The reference here is borrowed for the duration of the call and nothing is retained. That matters more than it looks: rules_for() hands back const Rule* pointing into the bundle, so those pointers are valid exactly as long as the bundle is. Everything that touches them does so inside this call.
Meaning
The whole rule catalogue — the baseline, every template, and which templates each host is assigned. Not this host's rules: the rules of the entire fleet, from which this host's are selected.
Read by
rules_for(bundle, facts.host_id) for the selection, and bundle.revision, which is copied onto the report as applied_revision so the server can tell which rules these answers were produced against.

facts — const HostFacts&

Origin
HostProbes::collect(bundle), called immediately before, on the same thread. That call reads the operating system: process list, service list, registry values, resources and adapters.
Lifetime
A temporary. It is built for this evaluation and destroyed after it — a photograph of the machine, not a window onto it. Nothing in the report points back into it; every string is copied out.
Meaning
What the machine actually is, right now. Note what collect() does first: it walks the same rules_for() list and probes only the categories some rule references. So an empty facts.processes can mean "no process rule applies here" as easily as "nothing is running" — which is safe only because, in that case, nothing reads it.
Read by
facts.host_id selects the rules. Then each rule kind reads its own field: process rules scan facts.processes, service rules facts.services, network rules facts.resources.adapters. Registry rules look up facts.registry by registry_key(), and here an absent entry is meaningful: it means the value was never probed, which reports Error, not Fail. "We did not look" and "it is not there" are different answers.

caps — Capabilities (by value)

Origin
HostProbes::capabilities(). Fixed at construction as the platform's declared capabilities intersected with the probes actually supplied, so a null probe can never advertise a capability nothing can serve.
Lifetime
A uint32_t bitmask passed by value — no aliasing, no lifetime question at all. Constant for the run of the client.
Meaning
What this agent is able to answer, which is not the same as what it found. This is the same number that travels in every ClientAnnounce and ends up on the server as FleetEntry::caps — one value in three places, which is why losing it on the server was a real bug and why the announce repeats.
Read by
The gate at the top of the loop: caps.has(required_capability(kind_of(rule))). A rule that fails it never reaches its evaluator — it yields NotApplicable with an observed naming the missing capability, deliberately without claiming an OS limitation, since evaluate() cannot tell "this platform cannot" from "that probe is not written yet".

How the three are used

The body is a single loop over the selected rules, with one gate and one dispatch. Everything interesting happens before the evaluator is reached.

What comes back

struct ComplianceReport {
    HostId        host_id;           // copied from facts.host_id
    uint64_t      applied_revision;  // copied from bundle.revision --
                                     // how the server spots a stale client
    vector<CheckResult> results;     // one per selected rule, in rules_for() order:
                                     // baseline first, then each assigned template
};

struct CheckResult {
    RuleId       rule_id;            // the only join back to the rule
    CheckStatus  status;             // Pass | Fail | NotApplicable | Error
    string       observed;           // "2 of 4 connected"
    string       message;            // Fail: what was expected instead
                                     // Error: why it could not be checked
                                     // Pass: empty
};

The report is self-contained: no pointers, no references, nothing borrowed from the bundle or the facts. That is what lets it be handed straight to the codec and published, and what lets the server cache it for as long as it likes.

reconcile() — who should be here, against who is

FleetView reconcile(const vector<ExpectedHost>&     expected,
                    const vector<DiscoveredClient>& discovered,
                    TimePoint                       now,
                    ReconcileOptions                options);

It runs on the server, on the GUI thread, once a second — and now also on every announce and every report, so a machine that has just spoken does not sit in the wrong state for up to a second.

expected — const vector<ExpectedHost>&

Origin
ServerController::effective_expected_hosts(): the operator's list, loaded from expected_hosts.json at startup, unioned with every host named in published_.assignments. Assigning a template to a machine is already a statement that you expect it, so making the operator type it into a second list only left the host sitting in Unexpected. Explicit entries win, because they carry the address.
Lifetime
A vector built fresh on every call and thrown away after it. The state that persists is the two things it is derived from, not this.
Meaning
The machines that ought to be there. Membership of this list is the only thing separating Missing from Unexpected — the same silence means opposite things depending on whether anyone asked for the machine.
Read by
The first loop, which produces one entry per expected host whether or not it has ever been heard from; and the set of ids the second loop tests against to find the strangers. address is copied through to the entry and never used for anything else — it is a note to the operator, not a route.

discovered — const vector<DiscoveredClient>&

Origin
ClientRegistry::snapshot(). Three different messages write into that registry: an announce records caps, a report records applied_revision, and a resource sample records nothing but the fact that the machine spoke. All three go through touch(), which advances last_seen only forwards, so a delayed or reordered message can never make a live client look stale.
Lifetime
The registry is long-lived and owned by the controller; the snapshot is a copy taken per call. Entries leave it only through mark_lost(), which the controller calls only for hosts that are not expected — an expected machine keeps its last timestamp so the lease check below can move it to Offline rather than having it vanish.
Meaning
Who has actually been heard from, and when. Note what it is not: it is not "who is connected". DDS liveliness has its own opinion, and it arrives as a separate callback; this is the record of messages received.
Read by
First collapsed into a map keeping the most recent sighting per host — the snapshot is already unique per host, but reconcile() does not assume its caller is well-behaved. Then looked up once per expected host, and iterated again to find the ones nobody expected.

now — TimePoint (by value)

Origin
Clock::now(), called at the call site — deliberately not inside. This one argument is what makes every liveness case testable: a test hands over a fixed instant and gets a deterministic answer, where a function that read the clock itself could only be tested by sleeping.
Lifetime
A value. It exists for the call.
Meaning
The instant the fleet is being judged at.
Read by
Only within_lease(): now - last_seen <= liveliness_lease. With one guard in front of it — a last_seen in the future counts as current rather than as an error, because that is clock skew on the client, and punishing a machine for having a fast clock helps nobody.

options — ReconcileOptions (by value)

Origin
A member of the controller. current_revision is refreshed from published_.revision immediately before every call; liveliness_lease is left at its default 10 s.
Lifetime
Two scalars, copied in.
Meaning
The two thresholds the classification needs. liveliness_lease matches the DDS Liveliness lease on the announce topic, so the two mechanisms agree about when a machine has gone quiet rather than racing each other. current_revision is the newest bundle the server has published.
Read by
The lease drives Online versus Offline. The revision drives one boolean: stale = applied_revision != current_revision, which is the fleet table's Revision column. Note it is inequality, not "less than" - a client on a revision the server has never published is just as wrong as one lagging behind.

How the four are used

The classification is a two-by-two: expected or not, heard from recently or not. There is no fourth row, because a machine nobody expects and nobody has heard from does not exist as far as the server is concerned.

In expected? In discovered? Within lease? State What the entry carries
yesno— Missing address only. No last_seen, no capabilities, stale = false — which is why the fleet table shows – in its adapter column rather than a zero.
yesyesyes Online address, last_seen, capabilities, staleness.
yesyesno Offline the same fields, still populated — this is the last thing the machine said before it went quiet.
noyes— Unexpected everything but the address, which nobody typed. Never lease-checked: a stranger that stops talking is removed from the registry outright instead.

One consequence of that last row is worth stating plainly. An expected host is never erased from the registry, so once it has been heard from it can never go back to Missing within a server run — it goes Offline and stays there. Missing means "not since this server started", which is also why every host is Missing for the first second after a restart.

What comes back

struct FleetView {
    vector<FleetEntry> entries;  // sorted most-urgent-first:
                                 // Missing, Offline, Unexpected, Online, then by host id
    FleetCounts        counts;   // online / offline / missing / unexpected / stale
};                               // counted in the same pass, so the ribbon and the
                                 // table can never disagree

struct FleetEntry {
    HostId              host_id;
    string              address;    // only ever from the expected list
    HostState           state;      // Missing | Offline | Unexpected | Online
    optional<TimePoint> last_seen;  // unset exactly when state is Missing
    bool                stale;      // applied_revision != options.current_revision
    Capabilities        caps;       // empty for Missing -- absent, not zero
};

The sort order is the argument for this being one function rather than a query interface. Urgency is decided once, here, and every view downstream inherits it — the fleet table, the status ribbon, and the Compliance tab, which ranks silent machines above failing ones for exactly this reason.

Neither function ever asks a question it was not handed the answer to. No clock, no file, no socket, no static. Everything above — which rules apply, what the machine looks like, what it can report, who is expected, who has spoken, what time it is, how long the lease runs — arrives as an argument. That is the whole reason 135 tests can cover this without a mocking framework, and why a liveness bug can be reproduced by passing a different now rather than by waiting.

Boundaries worth knowing

  • Everything reaches the network through ITransport. Fast DDS is one implementation; an in-memory bus is another, and that is what lets the whole client-server conversation run inside a unit test with no multicast and no waiting. It also keeps a second backend — OpenDDS was the original spec — addable rather than a rewrite.
  • Every OS call sits behind a probe interface, with public fakes shipped in lm/platform/fakes.hpp. A null probe means the capability is unavailable, and capabilities are intersected with the probes actually supplied — so a client can never advertise something it cannot serve.
  • A rule's id is the only join between the two ends. The wire carries results, not descriptions; each side recovers the display text from the bundle it holds. Ids are generated from the rule's kind and target rather than typed, because a reused id silently dropped a rule from evaluation.
  • lm_ui is shared by both applications — the theme, the meters, the sparkline, the adapter list. The client's detail window and the server's detail pane are built from the same widgets, so a reading cannot look like one thing on one screen and something else on another.
